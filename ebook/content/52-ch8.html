8

Open-Source-Core Products

When code is cheap to write, give it away and sell everything around it.
Learning objectives
  • Explain why giving code away can be a winning business strategy
  • Describe the revenue “below the waterline”: hosting, paid tiers, support, community
  • Choose a license that protects your business
  • Build a repository, a hosted cloud, and a community
  • Launch, monetize, and avoid giving away every reason to pay

Open-source software is software whose code is published for anyone to see, download, run, and modify, free. At first glance that sounds like a terrible business. Why give away your product? This chapter’s answer is that AI has made code cheap. Anyone can now generate an app’s code quickly, so the code itself is worth less every month.

What’s still hard to get is trust, a community, and distribution, meaning people actually finding and using your product. Giving the code away is the fastest way to earn all three. An open-source-core business then makes its money from everything around the code.

Key terms
Open source
Software whose code is publicly available under a license that lets others use, study, modify, and share it.
Self-hosting
Running software on your own servers instead of paying a provider to run it.
Hosted cloud
The vendor runs the software for you, handling setup, updates, backups, and uptime.
Open core
A free core product plus paid features for businesses.
License
The legal terms that define what others may do with your code.
Contributor license agreement (CLA)
An agreement that gives a project the rights it needs to code submitted by outside contributors.

The Model Explained

The iceberg

Above the waterline, “what people see”: the free public code. Below it, “where the money is”:

  • Hosting: most people don’t want to install, run, update, secure, and back up software themselves, so they pay you to run it.
  • Paid tiers: features businesses need, such as team permissions, single sign-on, audit logs, advanced analytics, and higher limits.
  • Support: guaranteed help, fast response times, setup assistance, custom work.
  • Community: sponsorships, events, partner marketplaces, certifications, and the goodwill that drives sales.

The free code brings users. What’s below the waterline turns some of them into customers.

The eight facts, unpacked

Why now. If anyone can recreate your code with AI, hiding it protects you less than it used to. Publishing it earns developers’ trust (they can inspect it), community contributions, and visibility.

Real-world examples. An open-source alternative to a big-tech app backend that most people pay to use as a hosted cloud, now a multi-billion-dollar company. An open-source product-analytics platform with public code and a paid cloud. An open-source scheduling tool, free to self-host, with paid hosted and enterprise versions. The common pattern is open code and a paid cloud.

Who builds it. Builders happy to work in public: sharing progress, answering questions in public issue trackers and chat, accepting outside contributions, and treating users as collaborators.

How it earns. Hosted cloud (the biggest earner for most), paid tiers, support contracts, and sponsorship.

The trap. Giving it all away with no reason to pay. Many popular open-source projects earn almost nothing because everything valuable is free and easy to self-host. Design the reason to pay from day one.

Why It Works, and Why It’s Growing

  1. Trust: businesses can inspect the code for security and quality, so there’s no black box.
  2. No lock-in fear: customers know they can self-host if your company disappears, which makes them more willing to buy your cloud.
  3. Free distribution: repository stars, developer news sites, self-hosting forums, and word of mouth replace expensive marketing.
  4. Free help and feedback: the community reports bugs, suggests features, writes integrations, and translates.
  5. An instantly understood pitch: “Like [expensive product], but open source and cheaper.” Every pricey software category is a target.
  6. Agents and developers lean toward open tools: popular open-source projects are well represented in what AI coding assistants know, so they tend to get recommended and used.

Choosing a License

The license decides what others may legally do with your code. Licenses fall along a spectrum from maximum adoption to maximum protection.

Table 8.2 • Common license choices
LicenseWhat it meansGood for
MIT / Apache 2.0Anyone can do almost anything, including selling a competing cloud service.Maximum adoption; libraries and developer tools
AGPLv3Anyone running a modified version as a web service must publish their changes.Apps where you want to protect your cloud business
FSL / BSL / similar source-availableCode is visible and usable, but competing services are prohibited; often becomes open source after 2–4 years.Strongest protection (purists don’t call these “open source”)
Open-core splitMain code under MIT or AGPL; an enterprise folder under a commercial license.Clean separation of free and paid features
Rule of thumb

For a full application you’ll sell as a cloud product, consider AGPL or a fair-source license, plus a separate commercial license for enterprise features. For a small library, use MIT. Have a lawyer look at your choice before launch, and use a contributor license agreement so outside contributions don’t complicate your licensing later.

Case study“StudioOS,” an open-source booking platform for fitness studios

The target. Boutique fitness studios (yoga, Pilates, climbing, martial arts) often pay $150–$500+ a month for booking software and complain about price and lock-in.

Above the waterline (free): class schedules, member booking, waitlists, basic memberships, email reminders. A tech-savvy owner can self-host it with one container command.

Below the waterline (paid): StudioOS Cloud at $49–$149 a month per studio (no servers, automatic updates and backups); Pro features (integrated payments with a small transaction fee, multi-location, a branded mobile app, an AI front-desk assistant, advanced reporting); a $500 migration service; support plans for franchises; equipment-brand sponsorships and a paid integrations marketplace.

Why customers pay: studio owners don’t want to run servers. The open code earns trust (“you’ll never be locked in”), and the cloud is the convenience they buy.

Stacking: StudioOS could add an ambient agent (Model 6) for the studio’s member chat, or collect consented, anonymized pricing and attendance trends across studios (Model 7).

Phase 0: Pick the project

  1. Choose a target: an open-source alternative to an expensive product people complain about; a tool you built for yourself that others in your field need; or a niche tool that doesn’t exist yet (combine with Models 2 or 5).
  2. Check demand: search software-alternatives directories for existing open-source options and gaps; search self-hosting and open-source forums for “is there an open-source alternative to…”; read review-site complaints about the incumbent’s price and lock-in.
  3. Design the reason to pay before writing code. Write down what’s free (enough to be genuinely useful), what’s paid (convenience, business features, compliance, support), and why a business would pay rather than self-host (setup time, maintenance, security, updates, backups, uptime).

Phase 1: Build the free core

Write it with an AI coding assistant on a modern web framework and a popular open-source database. Package it in containers with a single compose file for a one-command install, and later provide charts for large-company container orchestration. Offer one-click deploy buttons for popular app-hosting platforms and self-hosting dashboards. Host the code in a public repository with issues, discussions, and automated testing. Add dependency and security scanning and a SECURITY.md file, and automate releases and changelogs.

What a great open-source repository needs
  • A README that explains in ten seconds what it is and who it’s for, with a screenshot and a “quick start in two minutes”
  • One-command install
  • A clear LICENSE file
  • CONTRIBUTING guidelines, a code of conduct, and issue templates
  • “Good first issue” labels to welcome newcomers
  • A visible link: “Don’t want to self-host? Try our hosted cloud free.”

Phase 2: Build the hosted cloud

This is the main revenue engine. Use app-hosting platforms for simplicity, or major cloud providers and budget server hosts at scale; managed databases with automated backups; an authentication service (enterprise single sign-on is itself a great paid feature); a payment processor, plus a usage-billing or open-source-focused billing platform if you meter usage; license-key management for paid self-hosted features; and uptime monitoring, error tracking, and product analytics. Rule: the cloud must be noticeably easier than self-hosting, with instant sign-up, no setup, automatic updates, backups, and support.

Phase 3: Docs and community

Publish a documentation site (with an llms.txt file so AI assistants can learn your tool), a community chat server or forum, a public roadmap with feature voting, an email newsletter you own, sponsorship pages, and star-history tracking. Work in public: share weekly progress, publish a changelog, answer early questions quickly, and credit contributors.

Phase 4: Launch

  1. Developer news sites, with a “Show” post: “[Product], an open-source alternative to [category leader].” This is often the single biggest launch channel.
  2. Self-hosting and open-source forums, plus niche forums for your users.
  3. Product-launch sites for broader tech reach.
  4. Directories: software-alternatives sites, curated “awesome” lists, and container image registries.
  5. Video: “Here’s the free code anyone can run, and here’s the cloud version where it just works.” Self-hosting video creators love reviewing new tools.
  6. Comparison pages (“[Product] vs. [incumbent]”) for search traffic.

Phase 5: Monetize and grow

  1. Track the funnel: stars → installs (via opt-in telemetry) → cloud sign-ups → paying customers.
  2. Companies self-hosting the free version are your best leads for support and enterprise features.
  3. Add business features progressively: single sign-on, roles, audit logs, compliance certification, SLAs.
  4. Price in tiers: self-hosted $0; cloud starter and pro $19–$149/month; business $200–$1,000/month; enterprise $10,000–$100,000+ a year.
  5. Keep the free version genuinely good. Taking features away is the fastest way to lose community trust; add paid value on top instead.
  6. Optional funding: some investors specialize in open-source companies, but many open-source businesses are profitably bootstrapped.

Risks and How to Handle Them

RiskMitigation
No reason to pay (the trap)Design paid value up front: convenience, business features, support, compliance.
A large cloud provider resells your codeAGPL or a fair-source license for apps; enterprise features under a commercial license.
Maintainer burnoutClear contribution guidelines, issue templates, community moderators, saying no often, prioritizing paying customers.
Popular but not profitableWatch cloud conversion early; talk to companies using the free version.
Security vulnerabilitiesDependency scanning, a reporting process, prompt patches.
License confusionChoose on day one, use a CLA, get a short legal review.
Too technicalPartner with a developer co-founder, or start with a smaller tool built with an AI coding assistant.

Chapter summary
  • When code is cheap, giving it away buys trust, community, and distribution.
  • The money is below the waterline: hosted cloud, paid business features, support, and community.
  • Choose your license deliberately; AGPL or fair-source licenses protect a cloud business.
  • Make the cloud dramatically easier than self-hosting, and keep the free version genuinely good.
  • Design the reason to pay before you write the first line of code.
